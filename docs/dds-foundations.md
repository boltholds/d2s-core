# DDS: исходная модель и ограничения

**Статус:** Background / architectural assumptions. Источники — [references.md](references.md).

## Сущности

- **DomainId:** числовой идентификатор DDS-домена. Задаётся при создании DomainParticipant. Это логическая область обнаружения/обмена, не адрес устройства и не секрет.
- **DomainParticipant:** участник конкретного DDS-домена, владеющий локальными сущностями.
- **Topic:** имя + тип данных (и QoS-атрибуты) для согласованного обмена.
- **DataWriter / DataReader:** запись/получение экземпляров данных.
- **Publisher / Subscriber:** DDS-сущности, группирующие writers/readers.
- **Discovery:** протокол/сервис обнаружения участников и matching конечных точек.
- **QoS:** политика времени жизни и надёжности данных, истории, ресурсов и пр.

Разные DomainId обычно исключают стандартное взаимное обнаружение DDS-участников. Мост между доменами — отдельный компонент. Одинаковые DomainId в двух несвязных сетях не означают, что сети автоматически соединятся.

## DomainId и масштабирование

В Fast DDS DomainId представлен 32-битным беззнаковым значением; это **не означает**, что можно без изменений конфигурации использовать миллиарды независимых стандартных UDP-доменов на одном хосте. DDSI-RTPS использует схему портов, зависящую от DomainId и participant index. Для стандартных UDP-портов физические ограничения наступают значительно раньше, конкретный диапазон зависит от настроек и участников.

D2S не должна использовать числовой DomainId как глобальный уникальный идентификатор P2P-сети.

## DDS Partition != изоляция безопасности

PartitionQosPolicy влияет на совместимость endpoint matching внутри домена. Она не заменяет аутентификацию, криптографическую защиту, контроль разрешений и раздельные сети. Обнаружение и метаданные могут оставаться видимыми в пределах домена.

## Перенос данных

DDSI-RTPS описывает wire-протокол DDS. Наличие общего стандарта не устраняет различий в типах, QoS, discovery и расширениях реализаций. Совместимость проверяется тестами между конкретными версиями.

## Децентрализация

Нативный DDS допускает связь без центрального брокера и различные discovery-конфигурации. Но доступность multicast, NAT traversal, работа через межсетевые экраны и безопасность не возникают автоматически. Глобальная federation mesh — надстройка D2S и отдельная инженерная задача.

## Термины, которые нельзя смешивать

| Термин | Что означает |
|---|---|
| DDS DomainId | Числовой ID транспортного DDS-домена |
| Logical domain | Предполагаемая вершина графа D2S Federation |
| Node identity | Идентичность программного/физического участника |
| Topic | Типизированный канал данных |
| Physical route | Путь по физической сети/overlay |
| Authorization edge | Разрешение междоменной передачи определённых данных |

Один логический домен в будущем может быть развернут в одном или нескольких физических DDS-доменах; обратное отображение тоже возможно только при строгой проверке политики и отсутствии несанкционированных совпадений. Этот mapping ещё не утверждён.
